"keys" · SHADW KeyForge

Sign every build, license every player

"Dev keys" means three separate things. KeyForge keeps them apart so a leaked beta key never signs a patch.

G2 planned · foundation built

Studio signing keys

One per game. They sign every build manifest Forge produces, and the game checks the signature before it runs a patch.

Entitlement keys

Dev, beta, press, retail and per-feature (DLC), with device limits and an offline policy.

Service keys

For the game's own servers to call the licensing API and each other.

The section of the file it fills

"keys": { "tiers": ["dev", "beta", "retail"], "device_limit": 3 }

Today the suite checks this section's shape only. In G2 it becomes a KeyForge game registration.

What exists

  • Signed build manifests (kfb1): a studio build key signs the list of files; changed, missing and unlisted files are refused as tampered, in both the JavaScript and the Rust implementations.
  • KeyForge's core is Rust with a C ABI, so a Godot GDExtension or a Unity package can call it.
  • Planned custody: a browser key that cannot be exported for dev builds, a hardware key for retail, and never a retail key held on a server.

Not built yet

The hosted licensing API, the engine plugin and revocation. G2 closes when the licensing API runs as a shadw.cloud function, a game refuses an unsigned or tampered build, and a revoked beta key stops working on another node within one registry block. None of that runs yet, and no game on this site is licensed.
